1. Multi-Platform Ads Performance Pipeline & Self-Service Data Ops Console

Data Engineer · internal platform for the media team · ~60 scheduled ETL jobs across 8 ad & social platforms

Built and operate the agency's central advertising-data platform — around 60 scheduled ETL jobs pulling eight ad and social platforms into BigQuery, modelled in LookML and served through Looker, with a web console that lets the media team repair their own data instead of filing a ticket.

Problem: Media teams reconciled campaign numbers by hand against each platform's back office. When a figure didn't match or a day went missing, the only fix was to wait for a data engineer — and because Google, Meta, TikTok and Instagram each report a different object model and metric definition, there was no single place to compare spend across channels.
Action: Built a Flask ETL service exposing ~60 scheduled endpoints across TikTok, Meta, Google Ads, LINE, Lazada, RTB House, Search Console and a social-listening vendor; normalised all of them into one unified "single view" schema; modelled the serving layer in LookML and built the Looker dashboards on top. Then shipped a self-service console so the team can re-pull any platform, report and date range themselves.
Result: The media team now fixes missing days and back-office mismatches without data-engineering involvement, and spend is comparable across channels for the first time. Deployed as per-client instances for six brands across banking, insurance and platform verticals — and designed so a re-run can never double-count, which is what made handing the trigger to non-engineers safe.

Pipeline architecture:
A connector-per-platform design: every platform owns one module holding its authentication, API calls and transforms, and the endpoints are thin orchestrators. Each job runs the same contract — extract → transform with pandas → load to a staging table → MERGE ... WHEN MATCHED THEN DELETE against production → append. Nothing is ever written straight into a production table, so re-running a job is always idempotent.

Self-healing error handling:
Rather than loading yesterday only, every daily job re-pulls a rolling 14–15 day window and rewrites that whole window. Late-arriving conversions, retroactive platform corrections and an entire failed night all self-correct on the next scheduled run, with no manual backfill. Separate explicit date-range endpoints exist for deliberate historical rebuilds.

Monitoring:
Every job posts its outcome to a Google Chat webhook, so a job that didn't run is visible to the team the same morning instead of surfacing a week later as a wrong number in a client deck. A freshness check reports the most recent data date per channel into the same space.

Self-service console:
A web UI on top of the same service: a three-step wizard (platform → report → date range → Pull Data) with a live execution log and a results summary, plus a management tab for registering endpoints and per-client split views. This is the piece that moved day-to-day data repair from the data team to the people who actually notice the problem.

BI modelling:
Wrote the LookML views and explores over the unified tables and built the Looker dashboards for spend, engagement and conversions — one consistent set of dimensions regardless of which platform a row came from.

Working with the media team:
Ran sessions with the media team to map each platform's ads hierarchy — account → campaign → ad set / ad group → ad — and to agree on what each metric means where the platforms genuinely disagree. That shared vocabulary is what the unified schema encodes. I also wrote a Thai-language pipeline guide that walks through the five layers the data passes, which symptom points at which layer, and where to fix it — so the team can trace a suspicious number themselves.

Analyst corrections from a data-validation UI land in a correction inbox that is drained into the main table each hour — so a mislabelled post is fixed by the person who spotted it, not by an engineer.

3. Consumer Lending & Insurance Group — BigQuery FinOps & Cloud Run Enablement

Data Engineer · cost optimisation + client team training · ~65–75% reduction in daily warehouse spend

Cut the client's daily BigQuery bill by roughly two-thirds by putting a staging/cache layer underneath the dashboards that were full-scanning GA4 on every load — then trained their team to deploy and operate the refresh jobs themselves.

Problem: The customer-facing funnel and SEO dashboards queried GA4 export tables directly, so every dashboard load re-scanned hundreds of gigabytes across 500+ daily event tables — one view alone scanned around 300 GB per query. A dashboard that several people keep open all day turned into a four-figure daily spend, and loads took about 30 seconds.
Action: Rebuilt the seven heaviest views on a cache-plus-daily-refresh pattern: pre-aggregate into a partitioned staging table, refresh only the last seven days each night (GA4 lands late and gets amended), and freeze everything older. The dashboards then read the staging table instead of the raw export, so a dashboard load stops being a full scan.
Result: Daily BigQuery spend fell from roughly 1,000–2,000 THB to 400–500 THB — about a 65–75% cut — with dashboard loads down from ~30s to 1–2s. I then ran training for the client's team on deploying and operating Cloud Run jobs for batch data updates, so extending the pattern to the next expensive view is theirs to do, not a new request to us.
Click for more details
The pattern:
Partitioned cache table → one-time historical backfill → nightly incremental refresh via a Cloud Run job → the view reads the cache. Closed periods are merged rather than recomputed, so the cost of a refresh stays flat as history grows instead of climbing with it.

Why seven days:
GA4's export arrives late and gets amended after the fact. Refreshing a fixed trailing seven-day window absorbs that correction entirely without re-reading history — the specific thing that makes "just cache it" fail in a GA4 pipeline if you only refresh yesterday.

Scope:
Seven views — renewal funnel, new-motor funnel by model (including a v2 using distinct counts), and a monthly SEO traffic-and-conversion view aggregating three GA4 properties across two projects — plus UNPIVOT views that reuse a parent's cache instead of building their own. Rolled out progressively: the renewal funnel is live and carries the measured saving above; the remainder are built, documented and reduced to a one-command deploy, staged for rollout.

What was deliberately left alone:
Lead and booking figures that have to be real-time were kept querying their sources rather than cached. The point of the exercise was to stop paying for a full GA4 scan on every dashboard load, not to cache everything on principle — caching a cheap CTE that needs to be live would have traded a real requirement for a rounding error.

Always-on lead pipeline for car dealerships — ad and website form submissions land in the warehouse within the hour and fan out to the dealer group's CRM, branch sales inboxes and per-branch sheets.

Problem: Leads arrived from Facebook lead forms and the website in different places and different shapes. Sales branches found out late, nobody could tell which car model a lead was actually for, and duplicate or junk submissions were reaching the CRM — where a bad record costs a salesperson a phone call.
Action: Built a FastAPI service on Cloud Run: a real-time webhook for website forms, scheduled pulls for Facebook Lead Gen, then cleaning and product tagging, then three delivery paths — the dealer group's CRM over its SOAP-style API, per-branch Google Sheets, and templated Thai email to the right branch's sales team.

Click for more details
Lead hygiene:
Phone numbers normalised to +66, obvious junk filtered (repeated-digit numbers and similar spam patterns), deduplication on lead id, and test or internal submissions dropped before delivery rather than after. Product tagging is derived from which form the lead came through, so one campaign can collect for several models and still keep them distinguishable downstream.

Delivery reliability:
Every CRM API call and its response is written to a middleware log table. Alongside the hourly job there is a 30-day replay path, so a window that failed can be re-sent without duplicating what already arrived — the same idempotency discipline as the ads pipeline, applied where the cost of a duplicate is a confused customer rather than a wrong chart.

Branch routing:
Company and branch mapping plus lead-source derivation (lead form, website, messenger, LINE) so the CRM receives the attribution the sales team expects, and the notification email reaches the branch that will actually make the call.

A deliberate design choice:
Google Sheets is the shared coordination layer rather than a managed database — chosen because the sales team already lives in sheets, and a pipeline whose output nobody opens is worth less than a slightly inelegant one they use. Raw capture and the cleaned sales-facing view are kept as separate tabs so the system of record is never edited by hand.

Also on this account:
